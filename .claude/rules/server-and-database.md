# Server and database

- code that may run only on the server (database, secrets) lives in files ending in `.server.ts` - TanStack Start import protection then fails the build when client code imports one
- a server function (`createServerFn`) that routes or the browser call sits in `src/server` without the `.server` suffix, its body runs on the server and only an RPC call reaches the client - it returns just the fields the screen needs, `getSessionUser` from `#/server/session` is the reference
- environment variables are read only through `getServerEnv` from `#/config/env.server`, which validates them - `.env.example` lists every variable, the real values go into `.env.local`, which is never committed, and a required one also gets a fake value of the right shape in `tests/.env.test`, or no test can load the server
  - a variable is checked as strictly as its known format (`GOOGLE_CLIENT_ID` ends with `.apps.googleusercontent.com`, `GOOGLE_CLIENT_SECRET` starts with `GOCSPX-`), so a swapped or badly pasted value stops the server with its name - when a service changes the format of a value, the schema follows
- the database is Neon PostgreSQL in Frankfurt (`aws-eu-central-1`), reached through Drizzle ORM and the Neon WebSocket driver, which supports transactions
  - the running application connects with `DATABASE_URL_POOLED` through `getDb` from `#/server/db/client.server`
  - drizzle-kit (`pnpm db:generate`, `pnpm db:migrate`, `pnpm db:studio`) uses the direct `DATABASE_URL`, migrations are generated into `drizzle/` and committed
- every timestamp column is `timestamp(..., { withTimezone: true })`, so a moment means the same whatever the time zone of the server
- the signed-in person is read through `getSessionUser` from `#/server/session`, signing out is `authClient.signOut` - the server deletes the session and expires the cookie in one answer, the cookie even when the database does not respond, so the screen never waits for it and `/prijava` checks the session only on a server render
- a field the server owns is added to the user through `user.additionalFields` with `input: false`, so a request that sends it is refused - the column is added to `src/server/db/schema/auth.ts` with a migration, as the generator would write it
- our rules before a request reaches Better Auth are plain functions called in turn by one `beforeAuthRequest` (`#/server/auth-hooks.server`), each looking only at its own path
- attempts are limited by Better Auth, on only in production, with our limits per IP and path in `#/config/rate-limit` - sign-in 5 times a minute, the endpoints that send an email (sign-up, password reset) 5 times in 5 minutes, everything else 60 a minute
  - they are counted by our own `rateLimitStorage` (`#/server/rate-limit.server`) in our `rate_limit` table, not by the storage of Better Auth, whose window starts again with every allowed request, so requests a little rarer than the limit would add up without end
  - a window starts with the first request and the count goes back to zero when the whole window has passed - one statement counts and decides by the clock of the database, so parallel requests and several server instances get the same answer
  - a new window deletes the rows whose window ended longer ago than the longest rule, no cleanup job is needed for them
  - every sign-in to one email address is counted too, from any IP address and failed or not - 11 in 10 minutes (`SIGN_IN_PER_ADDRESS`), then `SIGN_IN_LIMIT_REACHED` before the password is checked (`limitSignInsPerAddress`), with `retryAfter`, the seconds until the window ends, which the form shows rounded up to whole minutes; the address is kept only as a SHA-256 hash, and one without an account counts the same
  - the limit is only as good as the client IP - `AUTH_IP_HEADERS` names the header the hosting puts it in, set when the hosting is chosen; a header with a chain of addresses and no trusted proxies gives no IP, and then every visitor shares one count
- every email goes through `sendEmail` from `#/server/email.server`, which sends it with Resend - without `RESEND_API_KEY` it is printed in the terminal in development, so a link from it can be opened there, and refused in production
  - until our domain is verified at Resend, its test sender reaches only the owner of the Resend account
  - every email is built with `buildActionEmail` from `#/server/email-template.server` - texts around one button, the link written out under it
  - an email Better Auth asks for is sent with `sendEmailInBackground` and not awaited, an answer that waited for it would be slower for an address with an account - on serverless hosting it needs `advanced.backgroundTasks` with the `waitUntil` of the hosting, or the send may be cut off
- a sign-up asks only for the address and the consent, no password and no name - it is our endpoint `/sign-up/request` (`signUpWithoutPassword` in `#/server/sign-up.server`), the sign-up of Better Auth with a password is turned off (`disableSignUp`), so no one sets a password on an address they do not own
  - it needs `acceptTerms: true` and refuses otherwise with `TERMS_NOT_ACCEPTED`, `termsAcceptedAt` is written from the server clock when the user is made
  - a new address gets a user with no password and an empty name, the name is shown as `DEFAULT_USER_NAME` (`#/config/user`) until the user sets one in the profile, nothing asks for it before
  - the answer is the same for every address, the owner learns the rest by email (`#/server/sign-up-email.server`): a link to set the password while the address waits, every sign-up sends a new one, or that the account exists, with the way to sign in - an account with a password also gets `/zaboravljena-lozinka?email=…`, which types the address in, an account of Google only is told to use its button and gets no password link, a password is added later in the profile
  - the link is a token of the password reset of Better Auth, valid 24 hours (`SET_PASSWORD_EXPIRES_IN`) and once, it opens `/postavi-lozinku` - the password saved there confirms the address, and only then can the user sign in (`requireEmailVerification`)
- Google is the recommended way in, on the sign-in and the sign-up page alike (`socialProviders.google`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` of the Google Cloud project, redirect URI `<BETTER_AUTH_URL>/api/auth/callback/google`) - the user picks the account every time (`prompt: "select_account"`)
  - Google confirms the address, so it joins a confirmed account with the same address - `applyGoogleProfile` (`#/server/google-profile.server`) runs as `mapProfileToUser` before the account is looked up, only for an address Google has proven
  - Better Auth joins only a confirmed account, the switch that turned this off (`requireLocalEmailVerified`) is deprecated and goes away - so an unfinished email sign-up of the address is confirmed first, one with no password, which no one else holds a way into; an unconfirmed account with a password keeps the guard
  - the name and the picture from Google fill only what is empty - an empty name, no picture - and never replace what the user set (`updateUserInfoOnLink` stays off)
  - a failure returns to the page Google was started on (`errorCallbackURL` of `useGoogleSignIn`) with `?error=<code>`, which `getGoogleSignInProblem` (`#/utils/google-sign-in`) reads as cancelled, expired or failed for the message above the Google block - an unknown code counts as failed; a start Better Auth cannot read returns to `/prijava` (`onAPIError.errorURL`) instead of its bare error page
  - the click is the consent, the text under the button says so on both pages, and `stampGoogleConsent` (`#/server/google-consent.server`) writes `termsAcceptedAt` from the server clock for a user Google makes
- the password reset gives the same answer for every address, its link is valid one hour and once, and a new password signs out every session (`revokeSessionsOnPasswordReset`)
  - an address not confirmed yet gets the link too - the link reached the owner of the address, so a password saved through it also confirms the address (`confirmAddressOnReset`)
  - the same page serves the first password of a new account at `/postavi-lozinku`, only its texts differ (`PASSWORD_LINK_TEXTS`)
  - tokens of every verification are stored as a SHA-256 hash (`verification.storeIdentifier: "hashed"`), so the table alone resets no password
  - the link in the email goes to Better Auth first, which checks the token and opens `/nova-lozinka` with it, or with `error=INVALID_TOKEN` for an expired, used or damaged one - the page then offers a new link, without either it asks to open the link from the email; the token stays in the address, so a refreshed page still works - it is single-use and valid one hour, so it is worth nothing once used
  - the email has a button and, under it, the whole link to copy, so a link is rarely damaged
- the browser talks to it through `authClient` from `#/services/auth-client`
- sign-in is Better Auth, `auth` from `#/server/auth.server`, its tables are generated into `src/server/db/schema/auth.ts` with `pnpm dlx auth@latest generate --config src/server/auth.server.ts --output src/server/db/schema/auth.ts`, then a migration is generated from them like for any other table
